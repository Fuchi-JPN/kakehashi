## 0. サマリー

- **課題**: REAP枝刈り済みローカルLLM（sh0wie版Qwen3.8-Flash-Next REAP-384等）はコーディング較正の副作用で日本語生成が破綻する。関連文書はこれを「日本語較正コーパスでREAPを再実行する」という数千円〜2万円・数日規模の中期プロジェクトで解決しようとしている。
- **本書の狙い**: それより遥かに低コスト・低リスクで、**今日から**着手できる代替/補完策として、日英/英日を自動翻訳するAPI Proxyを企画する。
- **調査結果**: 要件（LLMによる翻訳＋複数モデル登録＋429等でのフォールバック）を単体で満たす既製OSSは見つからなかった。最も近い候補（AdaptiveAPI）は翻訳バックエンドが単一モデル固定で、まさに今回必要な部分が欠けている。
- **推奨アプローチ**: 新規にAdaptiveAPI（C#/.NET, AGPL, 実績極小）を導入・改造するのではなく、**既にCOSTRA基盤として稼働中のzephel01/CodeRouterにプラグインを追加する**。CodeRouterの中核機能そのものが「複数プロバイダの登録と自動フォールバック」であり、車輪の再発明を避けられる。
- ただし1点、着手前に確認すべき未検証の前提がある（5節Phase 0）。検証結果次第では7節のStandalone Relay方式に切り替える。

## 1. 背景と目的

### 1.1 課題の整理

添付文書の実験結果を要約すると:

| 能力 | REAP-384（sh0wie版、コーディング較正） |
|---|---|
| 英語での推論・コーディング | 健全（HumanEval 92.1%、無枝刈り比-1.8pt） |
| 日本語の自由な文章生成 | 破綻（同一文の反復ループ、語彙崩壊） |

原因は較正データが「agentic-coding（英語）」に偏っており、日本語生成に必要なエキスパートが枝刈りで失われたためと推定されている。

### 1.2 なぜ「翻訳プロキシ」なのか

添付文書が提案する解決策（日本語コーパスでのREAP再較正）は筋が良い反面、以下の重さを伴う。

- qwen4_exp用アダプタの新規開発（`egesabanci/reap-mlx`は未対応）
- クラウドGPU数時間〜1日のレンタルと較正パイプライン構築
- 較正コーパスの構築・比率調整
- 「日本語創作特化」という**単一用途**にしか効かない（コーディング用途で日本語入出力したい場合は別途較正が必要）

一方、翻訳プロキシは以下の利点を持つ。

- モデルの重みには一切手を加えない。**どのローカルLLMに対しても即座に効く**（REAP-384に限らず288版でも、将来別のモデルに乗り換えても）
- 実装規模が小さい（既存インフラを流用すれば数百行規模）
- 失敗してもモデルを壊さない（プロキシを止めれば元通り）

両者は排他的ではない。翻訳プロキシは今日から使える保険であり、将来REAP日本語較正版が完成しても、翻訳プロキシは「コーディング較正版に日本語で指示を出したい」場面で有効であり続ける（12節）。

## 2. 既存OSS調査

### 2.1 比較表

| 候補 | 種別 | 言語 / ライセンス | 人間言語の翻訳機能 | 複数モデル+エラー時フォールバック | 評価 |
|---|---|---|---|---|---|
| LiteLLM / Portkey Gateway / model-chain-proxy 等 | 汎用LLM Gateway | 各種（主にMIT・Apache） | ❌ ここでの「翻訳」はAPIワイヤ形式の変換であり、自然言語の翻訳ではない | ✅ これらの中核機能そのもの | 実装パターンの参考にはなるが、翻訳機能自体がないため単体では要件を満たさない |
| **DeeJayTC/AdaptiveAPI** | LLM/MCP向け多言語プロキシ | C# / .NET 10 / **AGPL-3.0** | ✅ DeepLまたはLLM（`llm`翻訳バックエンド、任意のOpenAI互換エンドポイント指定可） | ❌ **翻訳バックエンドは単一モデル固定**（`Translators__Llm__Model`は単一値、既定`gpt-4o-mini`） | 要件に最も近いが、まさに必要な部分が欠けている。かつ★1・10コミット・単独開発者という実績の薄さがリスク |
| **zephel01/CodeRouter**（＋プラグイン群） | コーディングエージェント向けルーター | **Python 3.12+ / MIT** | ❌ 「Wire翻訳」はAnthropic↔OpenAIのAPI形式変換であり自然言語翻訳ではない | ✅ **中核機能そのもの**（ローカル→無料クラウド→有料の3層自動フォールバックが売り） | 既にCOSTRA基盤として運用中。翻訳機能はないが、フォールバック機構と実績あるプラグイン拡張パターンを流用できる **[本書の推奨路線]** |

### 2.2 DeeJayTC/AdaptiveAPI 詳細

「Drop-in multilingual proxy for LLMs, MCP servers, and any HTTP+JSON API」を掲げる、2026年公開の新しいプロジェクト。設計は非常に丁寧で、参考にすべき点が多い。

- **5段パイプライン**: ①Tokenise（コード・URL・ID等を`<adaptiveapi id="TAG_n"/>`プレースホルダで保護）→②Translate→③Verify（プレースホルダの完全一致を確認、不一致なら原文にフォールバック）→④Detokenise→⑤Re-emit
- **tool_calls対応**: `tool_calls[*].function.arguments`内のJSONを解析し、キーのdenylist（`id`/`uuid`/`email`/`slug`/`key`/`locale`/`tz`/`url`/`href`/`path`、および`*_id`/`*_code`/`*Id`/`*Code`パターン）で除外しつつ、実際の自然文だけを翻訳する
- **ストリーミング3方式**: 文末バッファ方式（既定）／プログレッシブ／応答完了後一括
- **翻訳バックエンド設定**: `Translators__Default`は`passthrough`/`deepl`/`llm`から選択。`llm`選択時は`Translators__Llm__BaseUrl`（任意のOpenAI互換エンドポイント）・`Translators__Llm__Model`（既定`gpt-4o-mini`）・`Translators__Llm__ApiKey`を指定 — **いずれも単一値**であり、複数モデルのフォールバックには対応していない
- **プラグイン機構**: `IAdaptiveApiPlugin`インターフェースと`IRequestTranslationHook`/`IResponseTranslationHook`フックが設計されているが、未マージの`feature-plugins`ブランチ上にあり、作者自身が「テストなし・サンプルプラグインなし・ドキュメントなし・認可まわりに要修正あり」と明記している（`PLUGINS_PLAN.md`）。今すぐビルドを乗せるには時期尚早
- **ライセンス**: AGPL-3.0。個人のLAN/VPN内利用のみであれば公開義務は発生しないが、将来的に外部公開する場合は改造版ソースの提供義務が生じる点に留意
- **実績**: ★1・Fork 0・コミット10・単独開発者（2026年開始）。技術的な設計思想は優れているが、本番運用の実績はほぼゼロ

**結論**: 機能面では最も近いが、(a) 複数モデルのフォールバックという核心要件が欠けている、(b) C#/.NETという不慣れなスタック、(c) AGPL、(d) 実績の薄さ、の4点から、これを`git clone`して改造するのは費用対効果が低いと判断する。ただし①〜③の設計（プレースホルダ方式・denylist・ストリーミング戦略）は、4.3節で示す通り**設計思想として流用**する。

### 2.3 zephel01/CodeRouter 詳細

既にCOSTRAの基盤として採用済みのルーター。当初の用途（コーディングエージェント⇄ローカルLLM間の仲介）とは別に、以下の理由で今回の改造対象として有力である。

- **技術スペック**: Python 3.12+、ランタイム依存は`fastapi`/`uvicorn`/`httpx`/`pydantic`/`pyyaml`の5個のみ（LiteLLMもLangChainもOpenAI/Anthropic公式SDKも使わない方針）。テスト1,500本以上。★47・Fork 2・347コミット。MIT
- **フォールバックエンジンが中核機能**: `providers.yaml`に`providers`（各プロバイダのbase_url/model/kind等）と`profiles`（プロバイダの優先順位付きリスト）を宣言するだけで、「①失敗→②へ、②失敗→③へ」の自動フォールバックが動く。429やOOM等はL2 Memory Pressureガードで検知し、該当プロバイダを一時cooldown除外してチェーン次点へフォールスルーする挙動が既にある
- **CJK比率検出が既に存在**: v2.6.0の「言語税トラッキング」機能で、リクエスト中のCJK文字比率を計測し`cjk_ratio_min`ルールでルーティングを分岐する仕組みが実装済み。これは「日本語が含まれるリクエストを検知する」ロジックとして翻訳要否判定に転用できる可能性がある
- **プラグイン拡張の実績**: `agent_cli`機能はv2.9.0で**コア実装からプラグイン`coderouter-plugin-agents`へ完全移設**された前例がある。さらに`coderouter-plugin-compress`（tool_result圧縮）は`InputFilter`という基底クラスを実装するだけの外部パッケージとして、「CodeRouterコア側は一切変更せず」に、圧縮・可逆復元(CCR)・Anthropicプロンプトキャッシュ境界の注入(CacheAligner)という3つの独立機能を実現している。設定は`providers.yaml`の`plugins.enabled: [compress, cache-align]`と`plugins.config.<プラグイン名>`で完結する
- **翻訳機能そのものは存在しない**: 「Wire翻訳」はAnthropic⇄OpenAIのAPIスキーマ変換であり、自然言語の翻訳とは無関係。今回必要な機能はゼロから追加する必要がある

**結論**: 人間言語の翻訳機能はないが、①要件の核心である「複数モデル登録+エラー時フォールバック」の実装土台が既に成熟した形で存在し、②プラグインとして機能追加する前例（compress）が実在し、③Pythonでスタックが一致し、④既に運用中のインフラである、という4点から、**改造の主軸はAdaptiveAPIではなくCodeRouterに置く**べきと判断する。

### 2.4 結論

既存OSSをそのまま採用するだけでは要件を満たせない。改造が必要という前提に立ち、改造対象は**新規にAdaptiveAPIを持ち込むのではなく、既存のCodeRouterにプラグインとして機能追加する**方針を推奨する（AdaptiveAPIの設計は参考として取り込む）。

## 3. 要件定義

### 3.1 機能要件

| ID | 要件 |
|---|---|
| FR1 | クライアント（コーディングエージェント等）から届いた日本語のプロンプトを、ローカルLLMへ転送する前に英語へ自動翻訳する |
| FR2 | ローカルLLMが返した英語の応答を、クライアントへ返す前に日本語へ自動翻訳する |
| FR3 | 翻訳に使うクラウドLLM（モデル・エンドポイント・APIキー）を優先順位付きで複数登録できる |
| FR4 | 現在使用中の翻訳バックエンドがエラー（429 Too Many Requests、5xx、タイムアウト等）を返した場合、次点のバックエンドへ自動的にフォールバックする |
| FR5 | 登録した翻訳バックエンドが全滅した場合でも、リクエスト全体を失敗させない（原文をそのまま通す等のフェイルセーフ動作。ログには残す） |
| FR6 | コードブロック・JSON・URL・ID・ツール呼び出しの引数キー等、翻訳すべきでない部分は翻訳対象から除外する |
| FR7 | 設定は`providers.yaml`相当の宣言的ファイルで完結し、コード変更を伴わずに翻訳バックエンドの追加・並び替えができる |

### 3.2 非機能要件

| ID | 要件 |
|---|---|
| NFR1 | Python実装。venv運用、systemd常駐を前提とし、Dockerには依存しない |
| NFR2 | 追加ランタイム依存は最小限に抑える（CodeRouter本体の「5依存のみ」方針に合わせ、`httpx`等の既存依存を再利用し新規依存の追加を避ける） |
| NFR3 | 可能な限りCodeRouterのコア本体を改造せず、プラグインまたは外部プロセスとして実現する |
| NFR4 | レイテンシよりコストを優先する既存方針に合わせ、翻訳による往復遅延の増加は許容する（ただし計測は行う） |

### 3.3 スコープ外（翻訳しないもの）

コーディングエージェント経由の利用を主眼に置くため、翻訳対象は**「ユーザーの自然文発話」と「モデルの最終自然文応答」に限定**し、以下は翻訳対象外とする。

- システムプロンプト（エージェントのスキャフォールディングは通常既に英語で構築されており、二重翻訳はコスト増と品質劣化を招く）
- ツール呼び出しの引数（JSON構造そのもの。ただし引数値の中に自然文が含まれる場合は要検討）
- ツール実行結果（ファイル内容・コマンド出力・grep結果等）
- コードブロック内部

## 4. アーキテクチャ

### 4.1 全体構成（Plugin方式の場合）

```
Kilo Code / Cline 等のコーディングエージェント（日本語で対話）
        │  (OpenAI互換 /v1/chat/completions)
        ▼
┌─────────────────────────────────────────────┐
│  CodeRouter（既存・COSTRA基盤）              │
│                                             │
│  [NEW] coderouter-plugin-translate          │
│    ┌─────────────────────────────────┐     │
│    │ InputFilter: リクエスト中の      │     │
│    │  user自然文を検出→JA→EN翻訳     │     │
│    │  （翻訳フォールバックチェーン）  │     │
│    └─────────────────────────────────┘     │
│                    │                       │
│         （3層フォールバックエンジン・       │
│          6系統ガード・tool-call修復は       │
│          既存のまま素通り）                 │
│                    │                       │
│    ┌─────────────────────────────────┐     │
│    │ [NEW] 応答側フック:              │     │
│    │  モデルの最終応答をEN→JA翻訳     │     │
│    │  （Phase 0で実現方式を確定）     │     │
│    └─────────────────────────────────┘     │
└─────────────────────┬───────────────────────┘
                       ▼
        ローカルLLM（REAP-384等、日本語破綻・英語健全）
```

翻訳自体の呼び出し先（＝翻訳フォールバックチェーンの中身）は、CodeRouterの`providers`定義を再利用し、既存のOpenRouter無料枠・Chutes等をそのまま登録する。**フォールバックロジックを2重実装しない**ことがポイント。

### 4.2 翻訳要否の判定

v2.6.0で実装済みのCJK比率計測ロジックを流用し、以下いずれかの方式を想定する（Phase 0で実装コストを見て選択）。

- **方式A（プロファイル単位の固定フラグ）**: `providers.yaml`のプロファイルに`translate: {enabled: true}`を明示。REAP-384を指すプロファイルにのみ適用し、常時翻訳する。判定ロジックが不要でシンプル
- **方式B（CJK比率ベースの自動判定）**: 既存の`cjk_ratio_min`相当の仕組みで「日本語が一定割合以上含まれる場合のみ」翻訳を起動。英語主体のターン（コードのみの指示等）で無駄な翻訳コストを避けられる

初期実装は**方式A**を推奨する（判定ロジックのバグが即座に「翻訳されない」という分かりやすい失敗で気づけるため）。

### 4.3 コード・JSON安全性（AdaptiveAPIの設計を踏襲）

AdaptiveAPIの5段パイプラインを簡略移植する。

1. **保護**: 翻訳対象文字列中のコードブロック（\`\`\`で囲まれた範囲）・インラインコード（\`で囲まれた範囲）・URL・UUID的な文字列を正規表現で検出し、`⟦PH_n⟧`のようなプレースホルダに置換して退避する
2. **翻訳**: プレースホルダを含んだテキストごと翻訳バックエンドへ送る（LLMベースの翻訳であれば大抵プレースホルダをそのまま保持して返すが、保証はない）
3. **検証**: 送出したプレースホルダの個数・内容が翻訳結果に過不足なく含まれるか確認する。不一致ならその回だけ原文パススルー＋ログ警告（AdaptiveAPIの`adaptiveapi_placeholder_integrity_failures_total`相当のメトリクスに倣う）
4. **復元**: プレースホルダを退避しておいた原文に戻す

### 4.4 設定スキーマ（案）

```yaml
# ~/.coderouter/providers.yaml に追記するイメージ

plugins:
  enabled: [translate]
  config:
    translate:
      mode: safe                    # off | safe（失敗時は原文パススルー）
      source_lang: ja
      target_lang: en
      apply_to_profiles: [local-ja-broken]   # 方式A: 明示指定
      protect_patterns: [code_block, inline_code, url, uuid]
      backends:                     # 翻訳専用の優先順位付きモデルリスト
        - name: translate-free-1
          base_url: https://openrouter.ai/api/v1
          model: <例: COSTRAで実績のあるOpenRouter無料枠モデル。要現行確認>
          api_key_env: OPENROUTER_API_KEY
        - name: translate-chutes
          base_url: <Chutesのエンドポイント>
          model: <Chutes契約内モデル>
          api_key_env: CHUTES_API_KEY
        - name: translate-paid-fallback
          base_url: https://api.anthropic.com
          model: claude-haiku-4-5-20251001
          api_key_env: ANTHROPIC_API_KEY
          opt_in: true               # ALLOW_PAID=true 時のみ有効
      retry:
        on_status: [429, 500, 502, 503, 504]
        on_timeout: true
        max_attempts_per_backend: 1   # 1回失敗したら次のbackendへ
```

`backends`のモデル名・エンドポイントは執筆時点で確定できないため、実装時に現行の契約状況（Chutes月額固定プラン・OpenRouter無料枠の現行ラインナップ）を確認して埋めること。

## 5. Phase 0: 着手前の検証（最重要・目安30分〜1時間）

改造の実現可能性は、CodeRouterのプラグイン機構が「通常のユーザー/アシスタント発話本文」まで対象にできるか、応答側にもフック可能かという**未確認の前提**に懸かっている。コーディングエージェントに実装を依頼する前に、以下を確認すること。

1. `zephel01/CodeRouter`と`zephel01/coderouter-plugin-compress`をcloneし、`InputFilter`基底クラスの実装（シグネチャ、呼び出しタイミング）を読む
2. `compress`プラグインの設定にある`targets: [tool_result]`が受理する値の全体（列挙値または文字列パターン）を確認し、**通常のuser/assistant発話本文を指す値が存在するか**を確認する
3. リクエスト側だけでなく、**モデル生成後の最終応答（レスポンス）に対してもプラグインからフック可能か**を確認する。コアの`output_filters`（`strip_thinking`等）がプラグインから拡張可能な設計か、または`OutputFilter`のような別インターフェースが存在するかを見る

**判定**:

- 2・3が両方YES → 6節（Phase 1a: Plugin方式）で実装する
- いずれかNO、または調査に時間をかけたくない → 7節（Phase 1b: Standalone Relay方式）に切り替える。この方式はCodeRouter内部構造への依存がゼロなので、Phase 0自体が不要になる

## 6. Phase 1a: 実装ロードマップ（Plugin方式）

Phase 0がYESだった場合のみ着手する。`coderouter-plugin-compress`のリポジトリ構成をテンプレートとして流用する。

1. **雛形作成**: `coderouter-plugin-compress`と同じ構成（`src/coderouter_plugin_translate/`、`pyproject.toml`、`tests/`、MIT）でリポジトリを新規作成
2. **翻訳フォールバッククライアント実装**: `backends`リストを順に試行し、指定ステータスコード・タイムアウトで次点へ移るシンプルな非同期関数。`httpx`（CodeRouterの既存依存と共通）のみで実装し新規依存を増やさない
3. **プレースホルダ保護ロジック実装**: 4.3節の保護→翻訳→検証→復元を関数化。単体テストでコードブロック混入時の非破壊性を検証する
4. **InputFilter実装**: リクエスト中のuser発話（Phase 0で確認したtargets値）を対象に、上記翻訳フォールバッククライアントでJA→EN変換する
5. **応答側フック実装**: Phase 0で確認した方式（OutputFilterまたは同等の仕組み）でEN→JA変換する
6. **設定読み込み**: `plugins.config.translate`ブロックのパースとバリデーション（pydanticはCodeRouterの既存依存なので追加コストなし）
7. **フェイルセーフ確認**: 翻訳バックエンド全滅時に原文パススルーとなることを結合テストで確認する

## 7. Phase 1b: 実装ロードマップ（Standalone Relay方式）

Phase 0でプラグイン方式が不可と判明した場合、または検証の手間を省いて即着手したい場合の代替案。CodeRouter内部には一切手を触れず、その手前にもう1段プロキシを立てる。

```
コーディングエージェント（日本語）
        ▼
┌───────────────────────────────┐
│ [NEW] translate-relay         │
│  (FastAPI, 単独プロセス)       │
│  1. JA→EN翻訳（フォールバック  │
│     チェーンはCodeRouter自身の │
│     "translate"プロファイルを  │
│     叩くことで実装。新規の     │
│     フォールバックロジックを   │
│     自前実装しない）           │
│  2. 翻訳済み英語リクエストを    │
│     CodeRouterの既存          │
│     "local-ja-broken"         │
│     プロファイルへ転送         │
│  3. 応答をEN→JA翻訳して返却    │
└──────────────┬────────────────┘
               ▼
      CodeRouter（無改造・既存のまま）
               ▼
      ローカルLLM（REAP-384等）
```

この方式の利点は、**CodeRouterを2つの目的（翻訳・本処理）で1回ずつ、プロファイルを変えて叩くだけ**なので、フォールバック機構を新規に書く必要が一切ないこと。新規に書くコードは実質「プレースホルダ保護」と「2回のHTTP呼び出しの中継」のみで、Plugin方式より実装量が少ない。欠点は、常駐プロセスが1つ増える運用上の手間と、ネットワークホップが1段増えるレイテンシ増（許容方針とはいえ計測は必要）。

手順:

1. `~/.coderouter/providers.yaml`に翻訳専用プロファイル`translate`を追加する（4.4節の`backends`をそのまま`providers`/`profiles`として登録するだけ。CodeRouterの標準機能のみで実現可能）
2. FastAPIで最小限の中継サーバーを実装する（4.3節のプレースホルダ処理＋2回の`httpx`呼び出し）
3. コーディングエージェントの向き先を`translate-relay`に変更する（CodeRouter単体を直接向いていたのを1段挟むだけ）

## 8. Phase 2: テスト・検証計画

| 観点 | テスト内容 |
|---|---|
| 基本往復 | 日本語の平文プロンプト→ローカルLLM→日本語応答が違和感なく返るか |
| コード混入 | コードブロック・ファイルパス・URLを含む日本語プロンプトで、該当部分が翻訳で破壊されないか |
| ツール呼び出し | エージェントが実際にツール呼び出しを行うターンで、tool_call引数やtool_result本文が誤って翻訳されないか |
| ストリーミング | ストリーミング応答時に翻訳が破綻なく機能するか（Plugin方式の場合、応答側フックがストリーミングに対応しているかはPhase 0で要確認） |
| フォールバック動作 | 翻訳バックエンド1番手を意図的に無効化（APIキー削除等）し、2番手へ切り替わることを確認する |
| 全滅時フェイルセーフ | 登録した翻訳バックエンドを全て無効化し、原文パススルー＋警告ログとなることを確認する |
| レイテンシ計測 | 翻訳なし直結時と比較した往復遅延の増分を計測し、体感への影響を確認する |
| 品質確認（創作用途） | 添付文書が扱う「創作・要約」タスクについて、翻訳を挟んだ場合の文体・ニュアンスの劣化度合いを主観評価する（数値ベンチでは測れない領域） |

## 9. コスト試算

翻訳に使う想定バックエンドは、いずれも既存契約の範囲内で賄える可能性が高い。

| 費目 | 想定 |
|---|---|
| OpenRouter無料枠モデル（Tier 1） | 追加費用なし（現行の空き枠次第。レート制限に当たった場合のためにフォールバックが必須という要件そのものの根拠でもある） |
| Chutes（月額固定プラン、Tier 2） | 既存の固定費内に収まる見込み（追加従量費用なし） |
| 有料API（opt-in、Tier 3） | 通常は起動しない想定。翻訳タスクは短文かつ低負荷なため、万一使っても1リクエストあたりのコストは軽微 |

REAP日本語再較正（添付文書7節: 数千円〜2万円のクラウドGPU代）と比較すると、本プロキシは**追加の金銭コストがほぼゼロ**で着手できる。

## 10. リスクと注意点

- **CodeRouterのプラグインAPIは非公式ドキュメント状態**: 単独開発者によるOSSであり、`InputFilter`等のインターフェースは将来のバージョンアップで変更される可能性がある。Phase 0の検証結果と、実装時点のCodeRouterバージョンをコメントとして残しておくこと
- **往復レイテンシの増加**: 翻訳を2回（入力・出力）挟むため、体感速度は確実に悪化する。コスト優先・レイテンシ許容という既存方針とは整合するが、無料枠モデルのレイテンシが大きい場合は特に顕著になる可能性がある
- **翻訳品質の限界**: 特に創作用途では、直訳的なニュアンス欠落が起きうる。コーディング用途の指示文（要件・エラーメッセージ等）は比較的翻訳の影響を受けにくいと予想されるが、8節のテストで実際に確認すること
- **二重翻訳コストの増大**: 翻訳バックエンド自体が429に当たりやすい状況（無料枠を多用している場合）では、フォールバックが頻発し実質的なレイテンシ・複雑度が上がる。フォールバック発生率も観測対象に含めるとよい
- **AGPL版（AdaptiveAPI）に立ち返る可能性も残す**: 本書はCodeRouterプラグイン方式を推奨するが、もしCodeRouterのプラグイン機構がPhase 0で「事実上使えない」と判明し、かつStandalone Relay方式でも要件を満たしにくい重大な制約が見つかった場合は、AdaptiveAPIをフォークして`Translators`層に複数モデル対応を追加する改造に立ち返る選択肢も残しておく（2.2節の設計は改造の出発点として十分詳細である）

## 11. REAPロードマップ（添付文書）との関係

添付文書の日本語較正ロードマップと本書の関係を整理すると次のようになる。

| | REAP日本語再較正 | 翻訳プロキシ（本書） |
|---|---|---|
| 対象 | モデルの重みそのもの | モデルの外側（入出力） |
| 効果範囲 | 較正した特定モデル・特定用途（日本語創作）のみ | **どのローカルLLMにも即座に適用可能** |
| 初期コスト | 数千円〜2万円＋アダプタ開発工数 | ほぼゼロ（既存インフラ流用） |
| 応答品質の上限 | モデル自体が「日本語で考える」ため理論上は翻訳越しより自然になりうる | 英語で思考した結果を機械翻訳するため、モデル自体の日本語能力向上は望めない |
| 適用タイミング | 中期（アダプタ開発・較正実行が必要） | 短期（即着手可能） |

両者は競合しない。**まず翻訳プロキシで当面の「日本語で使えない」を解消しつつ、並行してREAP日本語較正の検証（添付文書6.1節フェーズ0）を進める**のが合理的な進め方と考えられる。将来REAP日本語較正版が完成した場合も、翻訳プロキシは「コーディング較正版に日本語で指示したい」「別の言語破綻モデルを使う」といった場面で使い続けられる。
